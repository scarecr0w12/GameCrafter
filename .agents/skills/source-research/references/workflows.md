# Source research: scenario workflows

These are original worked recommendations. Fixtures and identifiers are hypothetical; substitute actual project contracts and supported tools.
Last researched: 2026-10-01.

## Worked request

**Request:** Investigate whether a narrative runtime supports branching and state.

**Initial investigation:** Open its own manual and installed-version references.

**Proposed action:** Record documented mechanisms and what integration behavior has not been executed.

**Expected handoff:** Dated source-backed note and proposed adoption/validation path.

## Coverage map

| Scenario | Decision or failure it exposes |
| --- | --- |
| Bound and source an API question | Attribution: Source directly supports the adjacent claim. |
| Verify and compare claims | Version: Compatibility assumed only when justified. |
| Write a dated note with defensible inferences | Unknown: Unverified labels instead of speculation. |
| Plan installed-version and live verification | Decision: Inference and user-confirmed requirement remain distinct. |

## Detailed scenarios

### 1. Bound and source an API question

- Use the question Can the installed narrative runtime serialize branching dialogue state for checkpoint restoration?

- Record installed package/runtime version, required state fields, and the proposed integration boundary.

- Find the runtime’s official manual, versioned reference, and own source/tests where useful; open the supporting pages.

- Locate the documented serialization mechanism and caveats rather than inferring support from a marketing feature list.

- If only default-branch docs are available, identify version drift and leave installed compatibility unverified.

- Deliver a bounded answer with direct URLs beside documented facts and a separate integration recommendation.

### 2. Verify and compare claims

- Build a comparison using the same criteria for each option: state persistence, supported runtime, authoring format, and validation.

- For each factual cell, keep a source location or explicit unverified label; silence in documentation does not prove absence.

- Check whether an official domain page is vendor-authored guidance, generated API reference, or community contribution.

- Open linked prerequisites and exceptions, such as dedicated-server limitations, before adopting an example.

- If sources conflict, prefer version-matching evidence and record the disagreement rather than silently choosing convenient wording.

- Keep a claim/source/version/confidence table; confidence is reviewer judgment, not vendor certification.

### 3. Write a dated note with defensible inferences

- Use purpose, sourced findings, recommended approach/caveats, and deduplicated sources under the requested research location.

- Place a URL adjacent to each factual assertion and label recommendations as original judgments.

- Record Last researched using the actual pass date; do not invent release, activity, or publication dates.

- For unavailable license, pricing, auth, or live capability details, write not verified in this pass with the missing scope.

- Use a concise paraphrase and link the full manual rather than copying extensive source text.

- Cross-check the note answers the original decision question without promoting a proposal into a user-confirmed requirement.

### 4. Plan installed-version and live verification

- Turn documented serialization support into a proposed fixture that saves mid-dialogue and restores the same choices/state.

- Name the actual runtime/tool invocation only after inspecting installed documentation or supported CLI help.

- If the runtime is unavailable, deliver source-backed findings and the fixture description without fabricated command output.

- Refresh source pages before promoting an old note into a current design assertion when version-sensitive details matter.

- Run repository link checks after saving a research note and identify whether external pages were opened separately.

- Report researched, locally inspected, and executed outcomes independently.

## Reviewable handoff

Include the requested result and the evidence specific to the scenarios above:

- Dated research note with near-claim URLs.
- Decision-relevant comparison or recommendation.
- Version/freshness caveats and live-verification gaps.

Keep proposed numbers, hypothetical fixtures, and unexecuted checks visible in the handoff. An authored plan or documented mechanism does not imply a successful runtime result.

## Acceptance assertions

- Factual claims cite opened sources that directly support them.
- Latest/unstable docs are not silently treated as installed stable behavior.
- Recommendations and inferences are labeled.
- Unknown license/pricing/runtime facts stay unverified.
