# Discussion board maintenance: scenario workflows

These are original worked recommendations. Fixtures and identifiers are hypothetical; substitute actual project contracts and supported tools.
Last researched: 2026-10-01.

## Worked request

**Request:** Organize a thread that chose server authority but left hosting unresolved.

**Initial investigation:** Read all decision comments and associated multiplayer tasks.

**Proposed action:** Summarize the confirmed authority choice and retain hosting as an open question.

**Expected handoff:** Linked decision/task summary with hosting visibly unresolved and read-back evidence.

## Detailed scenarios

### 1. Reconcile a mixed decision thread

- Use a hypothetical thread where the user confirms server authority while comments still disagree about hosting.

- Read the initial request and later corrections; identify the exact user message settling authority and its scoped conditions.

- Classify dedicated hosting, listen hosting, and host migration as proposals unless confirmation exists.

- Prepare a summary with Confirmed: server authority; Open: hosting model; Proposed: capability test and cost comparison.

- Link existing tasks to the confirmed decision without creating another task for the same authority work.

- Keep original messages and dissent visible through references; the summary must not rewrite a proposal as consensus.

### 2. Reconcile duplicates and task ownership

- Inspect two hypothetical tasks, NET-12 chest authority and NET-18 prevent duplicate chest rewards, for overlapping acceptance.

- Compare owner, state, artifact scope, prerequisites, and current work before recommending merge or cross-link.

- If one actor is already editing the shared network schema, expose that conflict rather than silently reassigning files.

- Use supported service task/claim operations only when discovered and authorized; do not invent board or lock method names.

- Propose a combined acceptance record while preserving each task’s history and any unique reconnect requirement.

- Deliver exact identifiers and suggested links/status changes; label the proposal unapplied when no mutation tool exists.

### 3. Update a stale completion summary

- Find a thread summary claiming network-tested when the linked artifact contains only mock RPC tests.

- Read its evidence and prepare a correction identifying passed contract checks and still-open separate-process verification.

- Check whether a later live result already resolves the gap before reopening tasks.

- Preserve earlier context as superseded evidence rather than deleting it or blaming the author.

- Use the supported update surface to apply only authorized summary/link changes and capture the returned record identifier.

- Read back the thread and task state; distinguish a prepared Markdown correction from an actual platform update.

### 4. Handle contradictions and unresolved questions

- When a later user message changes a checkpoint rule, identify affected earlier decisions and linked tasks.

- Record the new confirmed rule and mark the old summary superseded with a link to the resolving message.

- If two apparent confirmations conflict without a clear later correction, present the exact bounded decision needed.

- Let independent evidence collection or drafting continue without choosing an incompatible creative rule.

- Do not email or message external collaborators merely because a board mentions them; maintenance authorization is scoped.

- Deliver a decision/task/evidence reconciliation record containing actor, status, reason, and unapplied operations.

## Reviewable handoff

Include the requested result and the evidence specific to the scenarios above:

- Thread outcome map and proposed/applied changes.
- Decision/task/evidence links with preserved history.
- Read-back confirmation or explicit unapplied status.

Keep proposed numbers, hypothetical fixtures, and unexecuted checks visible in the handoff. An authored plan or documented mechanism does not imply a successful runtime result.

## Acceptance assertions

- User-confirmed decisions retain their actor and context.
- No title/status implies work completed without evidence.
- Links resolve to the intended thread/task/artifact.
- Actual updates are distinguished from a Markdown draft.
